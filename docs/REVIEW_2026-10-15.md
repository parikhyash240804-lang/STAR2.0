## Open findings

Priorities below are reviewer suggestions for development sequencing, not owner-approved requirements. All findings remain open; this documentation change fixes none of the application logic.

### R01 — configuration is disconnected from application execution (high; source verified)

`tools/make_brief.py:main` loads `FixtureProvider`, hard-codes NAV, sectors, initial holdings, mandate, path count/seed/horizon, drift and strategy parameters, and never reads `StarConfig` or an input workbook. There is no `star.pipeline`, application/configurator UI, or standard package CLI. The live-demo solve and nested historical strategy duplicate logic rather than invoking one shared strategy.

The two `BacktestSettings` classes are different types: the schema accepts `ME/3ME/6ME/YE`, while the runtime engine accepts `M/2M/Q/2Q/Y/W`. The schema's estimation window and signals mode are not consumed by that engine. Forecast engine/drift choice strings likewise need explicit mapping. An input template being readable does not mean its settings affect a run.

### R02 — historical provider guard is not armed (high; runtime and source verified)

`star/backtest/engine.py:run_backtest` constructs a physically truncated `DataView`, which is useful protection, but calls `strategy(...)` without `with view.armed()` and without `assert_no_future_data()`. A strategy that calls a provider separately, or closes over future data, escapes the claimed guard. A six-rebalance probe observed `GUARD.cutoff == None` on every call. Existing tests verify the view's frames stop at the date; they do not prove the provider guard is active in this loop.

The runtime also constructs the view without its optional benchmark/risk-free series even when those were supplied to `run_backtest`. Documentation saying all historical provider requests are structurally guarded overstates the current integration.

### R03 — reported mandate compliance exceeds what was checked (high; source verified)

`build_constraints` only adds liquidity/conviction/turnover constraints if the caller supplies their data/limits. It does not enforce holding counts, drawdown, expected shortfall or tracking error. Holdings selection is a separate `limit_holdings` function; the demo does not call it. The demo's table hard-codes the holdings row status to `ok`, and `LIMIT-00` claims count and exit-speed compliance from an empty `ConstraintSet.violations()` result even when those checks were never made.

The current demo happens to hold 24 names under a 25-name maximum; that is not evidence of enforcement. Its sector map cycles through five labels by ticker order, not actual company classification. ADV/liquidity inputs and a hard turnover cap are absent. Real inputs and explicit checked/not-checked states are prerequisites for an honest compliance statement.

### R04 — benchmark and portfolio-return conventions disagree with report prose (high; source verified)

The demo computes `bench = build_benchmark(...)` but passes raw `log(^NSEI / previous)` returns to simulation. Its full backtest equity comparison also uses that price series, and applies `log1p` to already-log returns before cumulating. The output nevertheless says it compares against NIFTY 50 plus dividends. The corrected benchmark helper exists but is not used consistently.

The simulation history is formed as `log_returns @ weights`; for a rebalanced portfolio the exact daily simple return is `simple_returns @ weights`, followed by `log1p` if log space is needed. The historical engine uses simple-return aggregation and drifting weights, so the two paths describe different portfolio mechanics. The demo calls Sharpe/confidence functions without a dated risk-free input (zero is the default); its simulation instead assumes a fixed 6% rate. Resolve conventions at shared boundaries before interpreting comparisons.

### R05 — displayed risk calibration is not an out-of-sample forecast test (high; source verified)

In the demo, `rolling_sd = port_daily.rolling(250).std().bfill()` includes the return being evaluated and back-fills early estimates from later data. `q99` is calibrated on all those standardised returns, then tested on the same sample. The portfolio weights themselves were selected at the final data date. A green traffic light here is not a held-out check of forecasts made the day before.

`tools/validate_models.py` similarly computes the empirical tail multiplier from the full evaluation sample's `z_scores` and scores that multiplier on the same returns. Its volatility walk-forward uses truncated views, but that does not make this separate VaR calibration held out. The historical doc's claim that every figure was fitted outside its graded period is too broad. Rebuild calibration chronology and report failed tests in their actual direction, rather than automatically claiming every rejection means understated risk.

### R06 — volatility bake-off uses unfinished forward targets (high; source verified)

`tools/improve_volatility.py` constructs 21-session future realised-volatility targets at five-session intervals. For test date `d`, its regression trains on every row whose forecast date is `< d`. Several of those targets end **after** `d`, so their outcomes were unknowable when that forecast was supposedly made. Training must be purged by outcome completion date, not just forecast-origin date.

This is separate from `star/estimators/har.py`, which fits using completed targets in the provided truncated frame. The shipped HAR forecaster and its research comparison are not the same evaluation implementation. `har.MEASURED` contains static constants; rerunning the research script only prints results and does not update them. The 0.385 R-squared / 24% gain / 66% attainable-ceiling claims therefore require a corrected rerun and versioned evidence; this review does not certify them.

### R07 — confidence and warnings are not fully grounded in the run (high; source verified)

`report/brief.py:_horizon_basis` assumes 1,250 sessions/five years rather than reading the actual sample. `build_brief_data` always sets `tail_ok = None`, so tail reliability never limits these badges. It can say Good despite unknown calibration inputs; its short-horizon cutoff also allows 6M without a horizon-only downgrade, unlike the persona's three-month rule.

The demo passes only `ts.warnings` into notes, omitting backtest survivorship/impact warnings and many estimator/data degradations. The full reviewed payload had an empty notes list even though the backtest lacks market-impact data. Report text saying the risk model is truthful or every limit passed is stronger than this evidence supports. `regime_state` also says the regime shapes the scenarios, but the demo simulates first and never passes regime weights into its bootstrap.

### R08 — simulation memory planner omits major allocations (medium; source verified, not profiled)

`forecast/engine.py:_plan_chunks` budgets one float32 value matrix and an estimate for chunk work. `simulate` also retains a float32 `max_dd` matrix and, when a benchmark exists, `bench_values`; percentile/partition operations and generator asset state require more memory.

For 756 days and 100,000 paths, the planner accepts a 512,000,000-byte budget (about 363 MB by its formula), but those three persistent matrices alone occupy about **908 MB**, before temporary arrays. No deliberately oversized allocation was run. Existing tests check the planner arithmetic and deterministic output under two budgets; they do not measure peak memory.

### R09 — forward-engine settings describe an unassembled path (medium; source verified)

The config defaults to `regime_fhs`, but the demo always selects ordinary `BootstrapGenerator` and an 8.5% assumed annual return (6% + half of a 5% premium). Core FHS and regime-weighted bootstrap helpers exist; there is no full fitted GARCH-residual plus Markov-switching regime orchestrator. Regime-weighted bootstrap uses independent weighted dates rather than block continuity. Drift sensitivity exists as a library function but is not displayed by the demo. Several modules still default/hard-code annualisation at 252 instead of consuming the measured calendar consistently.

### R10 — promised analyst workbook and persistent history are absent (medium; source verified)

The current `star/report` contains guidance and HTML only. Brief/guidance copy directs readers to an accompanying workbook for trades, provenance and diagnostics, but the demo writes none. The Excel input-template helper is a different artifact. The frozen legacy writes its old report, not the designed new analyst archive.

The HTML has preset horizons and scenarios only; there is no arbitrary-day input, custom shock editor, or full-page scenario recomputation. It starts its horizon selection at the first item, not the config's 3M default. Its key-metrics strip remains tied to the longest stored horizon. These are product gaps, not evidence that the implemented buttons fail.

### R11 — historical descriptions and tests overstate current guarantees (medium; source verified)

Examples to reconcile in future work:

| Existing description | Current implementation |
|---|---|
| Note 01: 20 HMM restarts, jump model, turbulence, absorption ratio and statsmodels cross-check shipped | Deterministic single-start HMM plus India VIX; other companions absent. |
| Note 02: tau is not exposed as a knob | `schema.py` and Excel layout expose tau. Mean posterior is tau-invariant under these Omega rules, but posterior covariance still depends on tau. |
| Note 03: Yang-Zhang is the default; nonlinear shrinkage/Dimson beta/factor attribution exist | HAR is the current default with Yang-Zhang fallback; linear shrinkage; ordinary beta helper; no current factor regression attribution. |
| Note 04: same guarded live/backtest strategy, all statistics shown | Callable backtest exists, but integration gaps R01/R02/R04/R05 remain; many metrics are library-only or absent. |
| Note 05: 97.5% ES headline, crisis covariance propagation, IL&FS episode | Risk API defaults include 97.5%, but forward engine stores 95/99 ES and brief uses 95%; stress functions are simpler than that design and IL&FS is not in the episode registry. |
| Note 06: cvxpy/fallback, blended smoothing, full regime-FHS and one matrix in memory | SciPy QP solvers; smoothing implemented as a turnover budget; R08/R09 apply. |
| Note 07: custom-day slider, Excel/native-chart exports and print QA | Preset HTML controls; no new workbook. |
| Package docstring: strict layer order enforced by a test | No general architecture-layer test found; the stated signals/views/pipeline/app layers are partly absent. |
| QP docstring: certificate compares sampled feasible points | Implementation compares multiple solver runs/starts; no sampled-point check or formal dual certificate. |

Some tests assert identities, numerical results and statistical power; others check strings or are weak guards. Examples: a calendar assertion ends `or True`; the HAR mean-vs-median test contains a placeholder and checks positivity rather than the correction's magnitude; several as-of tests compare already-truncated inputs. Passing these does not prove the stronger prose. Preserve useful regression tests while adding tests that reproduce the actual integration defects when fixing them.

### R12 — setup and boundary handling remain incomplete (medium; source/runtime verified)

No `pyproject.toml`, requirements/lockfile, packaged entry point or CI definition exists. Current success depends on the installed local environment. The schema does not validate its optional ES/tracking-error limits; negative values passed a direct validation probe. Direct estimator calls generally assume data is already truncated rather than enforcing the `as_of` stamp themselves.

Additional boundary limitations observed in source: stress generation catches broad exceptions and silently skips unavailable episodes (COVID is absent from the demo because the fixture begins in 2021); VaR forecast alignment falls back to positional pairing for equal-length differently indexed series; backtest cost deduction in daily returns is additive while NAV bookkeeping compounds the cost; trade statistics close on the last positive-weight day rather than the liquidation day under the engine's end-of-day weights. These need focused reproductions and regression tests before repair; no effect size was measured here.
